1. PROJECT OVERVIEW
================================================================================

RideShare AI Pro is a full-stack, real-time ride-sharing and parcel delivery
platform built as a final project for CSE 489 (Mobile Application Development).

The system consists of three interconnected components:
  (a) Flutter Mobile App — For Riders and Drivers (dual-role)
  (b) Node.js Backend API — RESTful server with Supabase PostgreSQL
  (c) React Admin Panel — Web dashboard for platform administrators

The platform enables riders to book motorcycle rides, send parcels, track
drivers in real-time via GPS, communicate through in-app chat, and pay via
cash, card, or bKash mobile banking. Drivers can go online/offline, accept
ride requests, verify passengers via OTP, navigate routes, and track earnings.

Total Features Implemented: 42 (39 MVP + 3 Bonus)

              └────────────────┘

Data Flow:
  1. Rider creates ride → Backend inserts into 'rides' table
  2. Supabase Realtime pushes INSERT event to Driver's Flutter app
  3. Driver accepts → Backend updates ride status + notifies Rider
  4. GPS tracking via Geolocator → periodic location updates to DB
  5. OTP verification via bcrypt hash comparison
  6. Payment processed → Commission split calculated (75/25)

────────────────────────────────────────────────────────────────────────────────
4.1 RIDER FEATURES (F1 – F17)
────────────────────────────────────────────────────────────────────────────────

F1: Phone Number Registration & OTP Login
  - Rider enters 11-digit Bangladesh phone number (+880 1XXXXXXXXX)
  - System generates 6-digit OTP, hashed with bcryptjs before storage
  - Rate limited: max 5 OTP requests per hour per phone number
  - Max 3 verification attempts per OTP
  - On success: JWT token generated (5-hour expiry) + user record created
  - New users auto-registered; returning users auto-logged in
  - Implementation: auth.routes.js → /api/auth/send-otp, /api/auth/verify-otp

F2: User Profile Management
  - Fields: full_name (min 3 chars), date_of_birth (must be 18+), email,
    photo_url, emergency_contact, language preference
  - Profile photo upload via image_picker → Supabase Storage
  - Implementation: users.routes.js → PUT /api/users/profile

F3: Interactive Map with OpenStreetMap
  - flutter_map with OpenStreetMap tiles (completely free, no API key)
  - Pickup location auto-detected via Geolocator GPS
  - Destination search with geocoding (Nominatim API)
  - Route polyline drawn between pickup and drop-off
  - Distance and duration calculated via OSRM routing engine
  - Map auto-fits to show entire route with padding
  - Implementation: rider_home_screen.dart (FlutterMap + MapController)

F4: Vehicle Type Selection
  - MVP: Bike (motorcycle) — base fare ৳30 + ৳12/km
  - Expandable architecture for Car, CNG, Auto-rickshaw
  - Vehicle type stored in rides table, linked to fare_rules table
  - Implementation: rider_home_screen.dart → _showFareEstimate()

F5: Dynamic Fare Calculation
  - Formula: Base Fare + (Distance × Distance Rate) + (Duration × Time Rate)
  - Surge pricing support (1.0x–3.0x multiplier based on demand)
  - Minimum fare enforcement (৳100 for car)
  - Fare rounded to nearest ৳5
  - Fare breakdown returned: base, distance, time, surge, total
  - Implementation: rides.service.js → getFareEstimate()

F6: Ride Booking System
  - Rider confirms booking after seeing fare estimate
  - System generates 4-digit pickup OTP (hashed with bcrypt)
  - Ride status set to 'searching_driver'
  - Ride record includes: pickup/drop coords, addresses, fare, OTP hash
  - Implementation: rides.service.js → createRide()

F7: Schedule-a-Ride (Future Booking)
  - Rider can schedule rides 1 hour to 7 days in advance
  - System creates 3 automated reminder jobs:
    • 15-minute reminder notification
    • 10-minute retry (find new driver if needed)
    • 5-minute final alert
  - Jobs stored in scheduled_ride_jobs table
  - Implementation: rides.service.js → createRide() (scheduled_at branch)

F8: Nearby Driver Search Algorithm
  - PostGIS-based proximity search within configurable radius (default 5km)
  - Filters: online status + verified documents
  - Sorted by acceptance rate (highest first)
  - Top 10 drivers receive ride_request records
  - Expandable to 10km radius if no drivers found
  - Implementation: rides.service.js → findNearbyDrivers()

F9: Real-Time GPS Tracking
  - Driver location tracked via Geolocator (every 5 seconds)
  - Location pushed to Supabase (drivers table: current_lat, current_lng)
  - Rider app subscribes to Supabase Realtime for live driver marker
  - Implementation: location_service.dart + active_ride_screen.dart

F10: Pickup OTP Verification
  - Rider receives 4-digit OTP upon booking (shown in app)
  - Rider shares OTP verbally with driver at pickup point
  - Driver enters OTP → backend compares bcrypt hash
  - Max 3 attempts; locked after 3 failures
  - Each attempt logged in otp_audit_log table
  - Implementation: rides.service.js → verifyPickupOTP()

F11: Route Progress Tracking
  - GPS telemetry points recorded during active ride
  - Data: latitude, longitude, speed (km/h), heading (degrees)
  - Stored in ride_route_points table for route replay
  - Implementation: rides.service.js → recordRoutePoint()

F12: In-App Real-Time Chat
  - Rider ↔ Driver text messaging during active rides
  - Chat only enabled when ride status is: driver_assigned, arrived, started
  - Messages stored in chat_messages table (Supabase)
  - Real-time delivery via Supabase Realtime subscriptions
  - Read receipts (is_read flag + unread count endpoint)
  - Message types: text (expandable to image, location, voice)
  - Implementation: chat.routes.js + chat_screen.dart

F13: Cash Payment
  - After ride completion, rider selects "Pay Cash"
  - Driver confirms cash received
  - Commission auto-calculated: 75% driver + 25% platform
  - Payment record created in payments table
  - Implementation: payments.routes.js → POST /api/payments/cash

F14: Digital Payment (bKash + Card)
  - bKash Tokenized Checkout (Sandbox integration)
  - WebView-based payment flow inside Flutter app
  - Steps: Create payment → Redirect to bKash → Callback → Execute
  - Card payment via Stripe (mock/placeholder, production-ready structure)
  - Saved payment methods for repeat use
  - Implementation: payments.routes.js → /api/payments/bkash/create

F15: Bilingual UI Support
  - Language toggle: English ↔ Bangla (বাংলা)
  - Language preference stored in user profile (users table)
  - Instant switch without app restart
  - Implementation: users.routes.js → language field in profile

F16: Rating & Review System
  - After ride completion, both rider and driver can rate each other
  - Rating: 1–5 stars + optional text comment
  - Duplicate prevention: unique constraint on (ride_id, rated_by)
  - Average rating auto-recalculated on each new rating
  - Low rating threshold (< 4.0) flags for admin review
  - Implementation: ratings.routes.js → POST /api/ratings

F17: Push Notifications
  - FCM (Firebase Cloud Messaging) token registration
  - Notification types: driver_accepted, ride_started, ride_completed,
    payment_confirmed, ride_cancelled, document_approved/rejected
  - Stored in notifications table with read/unread status
  - Implementation: notifications.service.js → sendNotification()

4.2 DRIVER FEATURES (F19 – F31)
────────────────────────────────────────────────────────────────────────────────

F19: Driver Registration
  - Same phone OTP flow as rider, but role = 'driver'
  - Auto-creates record in 'drivers' table with default values
  - verification_status = 'pending' until admin approves
  - Implementation: auth.routes.js (role parameter)

F20: Document Upload & Verification
  - Required documents: NID (front + back), Driving License, Vehicle Photo
  - Optional: Bank account details for direct settlement
  - Files uploaded via image_picker → Supabase Storage buckets
  - Document URLs stored in driver_profiles table
  - Implementation: driver_document_screen.dart + users.routes.js

F21: Verification Status Tracking
  - Status lifecycle: UNVERIFIED → PENDING → APPROVED / REJECTED
  - Driver can check real-time status from Profile screen
  - Backend returns verification_status from driver_profiles table
  - Admin panel shows pending verifications for review
  - Implementation: driver_profile_screen.dart → API /users/driver/verification-status

F22: Go Online / Go Offline Toggle
  - Driver toggles availability status: online ↔ offline
  - When going online: GPS tracking starts, location updated in DB
  - When going offline: GPS stops, removed from driver search pool
  - Status options: online, offline, break, busy
  - Implementation: driver_home_screen.dart → _toggleOnline()

F23: Incoming Ride Request Notification
  - Supabase Realtime subscription on 'rides' table
  - Filters for INSERT events where status = 'searching_driver'
  - Beautiful pop-up dialog shows: pickup/drop addresses, fare, distance
  - Accept/Decline buttons with timeout
  - Implementation: driver_home_screen.dart → _listenForRides()

F24: Accept / Decline Ride
  - Accept: ride.driver_id = current driver, status → 'driver_assigned'
  - Optimistic locking: prevents double-acceptance by multiple drivers
  - Decline: logged in ride_requests table, stats updated
  - Acceptance rate tracked: total_accepts / total_requests × 100
  - Other pending requests for same ride auto-expired
  - Rider notified via push notification on acceptance
  - Implementation: rides.service.js → acceptRide(), declineRide()

F25: Navigation to Pickup Point
  - After accepting, driver sees pickup location on map
  - Route polyline drawn from driver's current location to pickup
  - Turn-by-turn navigation ready (via external maps app)
  - Implementation: active_ride_screen.dart (driver mode)

F26: OTP Entry at Pickup
  - Driver enters 4-digit OTP given by rider
  - Backend verifies against bcrypt hash stored at booking time
  - On success: ride status → 'arrived', otp_verified = true
  - On failure: attempt counter incremented, max 3 attempts
  - Implementation: rides.service.js → verifyPickupOTP()

F27: Start Ride
  - After OTP verified, driver taps "Start Ride"
  - Ride status → 'started', started_at timestamp recorded
  - GPS tracking intensifies (route points recorded)
  - Rider notified: "Your trip has started. Have a safe journey!"
  - Implementation: rides.service.js → startRide()

F28: Navigation During Ride
  - Live map tracking during active ride
  - Route polyline from current location to drop-off
  - Real-time GPS telemetry recording (lat, lng, speed, heading)
  - Implementation: active_ride_screen.dart

F29: Complete Ride
  - Driver taps "Complete Ride" at destination
  - Fare recalculated based on actual distance/duration
  - Ride status → 'completed', completed_at timestamp set
  - Driver status → back to 'online' (available for new rides)
  - Driver's total_rides counter incremented
  - Rider notified with final fare amount
  - Implementation: rides.service.js → completeRide()

F30: Earnings Dashboard
  - Today's earnings: sum of driver_earning from completed payments
  - Today's trip count
  - Running total across all completed rides
  - Commission breakdown: 75% driver / 25% platform
  - Implementation: payments.routes.js → GET /api/payments/earnings

F31: Acceptance Rate Tracking
  - Formula: (total_accepts / total_requests) × 100
  - Updated on every accept/decline action
  - Higher acceptance rate → priority in driver search results
  - Stored in drivers table: acceptance_rate (float)
  - Implementation: rides.service.js → acceptRide(), declineRide()

7. SECURITY IMPLEMENTATION
================================================================================

  1. OTP Hashing:       bcryptjs with salt (plain text never stored)
  2. JWT Authentication: HS256 algorithm, 5-hour expiry for users, 1-day admin
  3. Rate Limiting:      5 OTP requests/hour per phone, 50/hour per IP
  4. Role Authorization: middleware checks rider/driver/admin roles per route
  5. CORS:              Configured for allowed origins
  6. Helmet:            Security headers (XSS, Clickjacking protection)
  7. Input Validation:  Phone format, rating range, required fields checked
  8. Optimistic Locking: Ride acceptance uses status check to prevent races

================================================================================
8. REAL-TIME SYNCHRONIZATION
================================================================================

The system uses Supabase Realtime (PostgreSQL Change Data Capture) for
instant synchronization between Rider and Driver apps:

  SYNC-1: Ride Acceptance
    Driver accepts → Rider instantly sees driver assigned (< 100ms)

  SYNC-2: OTP Verification
    Driver verifies OTP → Rider sees "Driver Arrived" status

  SYNC-3: Ride Start
    Driver starts ride → Rider sees live GPS tracking begin

  SYNC-4: Ride Completion
    Driver completes → Rider sees final fare + payment prompt

  SYNC-5: Rating
    Rider submits rating → Driver's average rating updated immediately
