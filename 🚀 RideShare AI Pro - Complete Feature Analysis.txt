Feature 1: Phone-Based User Registration
Description:
 User phone number দিয়ে register করতে পারবে। কোনো password লাগবে না initial registration এ।
User Story:
 "As a new user, আমি আমার phone number দিয়ে register করতে চাই যাতে আমি app use করতে পারি"
Detailed Requirements:
INPUT:
- Phone number (11 digits, starts with 01)
- User selects role: Rider or Driver


PROCESS:
1. User phone number enter করে
2. System validates:
   - Phone number format correct?
   - Phone number already exist করে না?
3. System sends 6-digit OTP via SMS
4. User OTP enter করে
5. System verifies OTP
6. If correct:
   - Create user account
   - Generate unique user ID (UUID)
   - Create JWT token
   - Login user automatically
7. If wrong:
   - Show error
   - Allow retry (max 3 attempts)


OUTPUT:
- User account created
- User logged in
- Token stored in device
- Redirected to profile completion screen


VALIDATION RULES:
- Phone must be exactly 11 digits
- Phone must start with '01'
- Phone must be unique
- OTP valid for 5 minutes
- Max 3 OTP attempts
- Max 5 OTP requests per phone per hour (prevent spam)


Implementation Approach:
TECHNOLOGY CHOICE:


Option 1: Supabase Auth + Twilio
- Supabase: User management, JWT tokens
- Twilio: SMS OTP delivery
- Flow:
  1. User enters phone
  2. Backend calls Twilio API → Send OTP
  3. Twilio delivers SMS
  4. User enters OTP
  5. Backend verifies OTP
  6. Supabase creates user session


Option 2: Custom Backend + any SMS provider
- Express.js backend
- PostgreSQL for users table
- SMS gateway (Twilio/Nexmo/BulkSMS BD)
- JWT library for tokens


RECOMMENDED: Supabase + Twilio
Why: Faster, built-in security, less code

COMPONENTS NEEDED:
1. Registration Screen (UI)
2. OTP Input Screen (UI)
3. Phone validation logic
4. OTP generation logic (random 6 digits)
5. OTP storage (Redis - 5 min expiry)
6. OTP verification logic
7. User creation logic
8. JWT token generation
9. Session management


DATABASE TABLES:
users:
- id (UUID)
- phone (VARCHAR, unique)
- role (ENUM: rider, driver)
- status (ENUM: active, blocked)
- created_at


otp_verifications:
- phone (VARCHAR)
- otp_code (VARCHAR, encrypted)
- attempts (INT)
- expires_at (TIMESTAMP)
- created_at


SECURITY MEASURES:
- OTP encrypted in database
- Rate limiting (5 requests/hour per phone)
- IP rate limiting (50 requests/hour per IP)
- OTP expires after 5 minutes
- Max 3 wrong attempts → temporary block

Feature 2: User Profile Management
Description:
 User তার personal information add/edit করতে পারবে
User Story:
 "As a registered user, আমি আমার profile complete করতে চাই যাতে অন্যরা আমাকে identify করতে পারে"
Detailed Requirements:
PROFILE FIELDS:


MANDATORY (Must complete):
- Full name
- Photo
- Date of birth (for age verification)


OPTIONAL:
- Email
- Emergency contact (name + phone)
- Preferred language (Bangla/English)


FOR DRIVERS (Additional mandatory):
- NID card photo (front + back)
- Driving license photo
- Vehicle type (Bike/CNG/Car)
- Vehicle model
- Vehicle registration number
- Vehicle photo
- Bank account details (for payouts)


PROCESS:
1. User navigates to profile screen
2. Fills required fields
3. Uploads photos
4. System validates:
   - Name: at least 3 characters

   - NID/License: readable, not expired
5. System saves to database
6. For drivers: Submit for admin verification


OUTPUT:
- Profile completed
- For riders: Can start booking rides
- For drivers: Status = "Pending Verification"

Feature 3: Driver Document Verification (Admin)
Description:
 Admin manually verify করবে driver এর uploaded documents
User Story:
 "As an admin, আমি driver documents verify করতে চাই যাতে শুধু verified drivers app এ active হয়"
Detailed Requirements:
ADMIN CAPABILITIES:
- View list of pending driver verifications
- View driver details and uploaded documents
- Zoom in on photos
- Download documents
- Approve driver
- Reject driver (with reason)
- View verification history
- Search/filter drivers


VERIFICATION CHECKLIST:
□ NID card clear and readable?
□ NID number visible?
□ Photo on NID matches profile photo?
□ NID not expired?
□ Driving license valid?
□ License number visible?
□ License not expired?
□ Vehicle photo clear?
□ Registration number matches document?
□ Vehicle in good condition?
□ Bank account details complete?


DECISION ACTIONS:
APPROVE:
- Driver status: pending → active
- Driver can go online
- Driver can accept rides
- Send notification: "Congratulations! You're verified"


REJECT:
- Driver status: pending → rejected
- Must provide reason
- Driver can re-upload documents
- Send notification: "Documents rejected. Reason: [reason]"


WORKFLOW:
1. Admin logs in
2. Sees dashboard: "12 drivers pending verification"
3. Clicks on a driver
4. Views all documents side-by-side
5. Checks each document against checklist
6. Makes decision (approve/reject)
7. System updates driver status
8. Driver notified


Implementation Approach:
TECHNOLOGY:


Admin Panel: React.js web app
Backend: Same as main app
Database: PostgreSQL
Real-time updates: Supabase Real-time or WebSocket

4. Zoom in/out
5. Center map on current location (button)
6. Show nearby landmarks
7. Search locations (autocomplete)
8. Select pickup location (tap on map or search)

- Request location permission on first use
- Handle permission denied gracefully
- Show why permission needed

CALCULATION LOGIC:


function calculateFare(pickup, drop, vehicleType) {
  // Step 1: Get distance and time
  directions = call Google Directions API
  distance = directions.distance (in km)
  time = directions.duration (in minutes)
  
  // Step 2: Get fare rules
  rules = fetch from database WHERE vehicle = vehicleType
  baseFare = rules.base_fare
  distanceRate = rules.distance_rate
  timeRate = rules.time_rate
  
  // Step 3: Calculate base fare
  distanceFare = distance × distanceRate
  
  // Step 4: Calculate time fare (if slow traffic)
  expectedTime = (distance / 40) × 60  // Expected time in normal traffic
  if (time > expectedTime) {
    extraTime = time - expectedTime
    timeFare = extraTime × timeRate
  } else {
    timeFare = 0
  }
  
  baseTotalFare = baseFare + distanceFare + timeFare
  
  // Step 5: Apply surge
  surgeMultiplier = get from Redis or calculate
  finalFare = baseTotalFare × surgeMultiplier
  
  // Step 6: Apply minimum fare
  if (finalFare < rules.minimum_fare) {
    finalFare = rules.minimum_fare
  }
  
  // Step 7: Round
  finalFare = round to nearest 5
  
  return {
    distance: distance,
    estimatedTime: time,
    baseFare: baseTotalFare,
    surgeMultiplier: surgeMultiplier,
    finalFare: finalFare,
    breakdown: {
      base: baseFare,
      distance: distanceFare,
      time: timeFare,
      surge: finalFare - baseTotalFare
    }
  }
}


SURGE CALCULATION:


Rule-based (MVP):
function calculateSurge(location, time) {
  // Get active rides and available drivers in area
  activeRides = count rides in 5km radius WHERE status IN ('searching', 'assigned')
  availableDrivers = count drivers in 5km radius WHERE status = 'online'
  
  // Calculate demand/supply ratio
  if (availableDrivers == 0) return 3.0  // Max surge
  ratio = activeRides / availableDrivers
  
  // Base surge on ratio
  if (ratio < 0.5) return 1.0       // Low demand
  if (ratio < 1.0) return 1.2       // Normal
  if (ratio < 2.0) return 1.5       // Moderate
  if (ratio < 3.0) return 2.0       // High
  return 3.0                         // Peak
  
  // Time-based adjustments
  hour = current hour
  if (hour >= 8 && hour <= 10) surge × 1.2  // Morning rush
  if (hour >= 17 && hour <= 20) surge × 1.2 // Evening rush
  
  // Weather adjustments (future)
  if (raining) surge × 1.3
  
  return surge (capped at 3.0x maximum)
}

Requirements:
Fare Components:
                                                * Base fare (varies by vehicle type: Bike 40, CNG 60, Car 80 BDT)
                                                * Distance fare (per km rate: Bike 20, CNG 25, Car 30 BDT/km)
                                                * Time fare (2 BDT/min if traffic is heavy)
                                                * Surge multiplier (1.0x to 3.0x based on demand)
                                                * Minimum fare enforcement (Bike 60, CNG 80, Car 100 BDT)
Calculation Formula:
                                                * Get distance and time from Google Directions API
                                                * Base fare + (Distance × Rate) + (Extra time × Rate)
                                                * Apply surge multiplier
                                                * Round to nearest 5 BDT
Display:
                                                * Show estimated fare before booking
                                                * Break down costs (base, distance, surge)
                                                * Highlight surge pricing clearly
                                                * Update dynamically if location changes
Flow:
                                                1. User selects pickup and drop locations
                                                2. System calls Google Directions API
                                                3. Gets distance (km) and duration (minutes)
                                                4. Fetches fare rules from database
                                                5. Calculates base fare
                                                6. Gets current surge multiplier
                                                7. Applies surge → Rounds fare
                                                8. Shows breakdown to user with total

Feature 4: Fare Calculation
কী: Booking এর আগে estimated fare দেখাবে
Scenario:
Ahmed pickup ও drop select করেছে:
Pickup: Gulshan 2
Drop: Dhanmondi 27


System calculates:


STEP 1: Get distance & time
- Backend calls Google Directions API
- Response:
  • Distance: 8.3 km
  • Duration (no traffic): 18 min
  • Duration (with traffic): 25 min


STEP 2: Fetch pricing rules
- Database query:
  SELECT * FROM fare_rules WHERE vehicle_type = 'bike'
- Result:
  • Base fare: ৳40
  • Distance rate: ৳15/km
  • Time rate: ৳2/min
  • Minimum fare: ৳60


STEP 3: Calculate base fare
- Formula: Base + (Distance × Rate) + (Time × Rate)
- Calculation: 40 + (8.3 × 15) + (25 × 2)
- = 40 + 124.5 + 50
- = 214.5


STEP 4: Check surge (if any)
- Current time: 6:30 PM
- Rush hour check: Yes (5-8 PM)
- Surge multiplier: 1.5x
- Apply: 214.5 × 1.5 = 321.75


STEP 5: Round & validate
- Round to nearest ৳5: 322 → 320
- Check minimum: 320 > 60 ✓
- Final fare: ৳320


STEP 6: Show to user
Ahmed sees:
┌──────────────────────────┐
│ Select Vehicle Type      │
├──────────────────────────┤
│ 🏍️ Bike      ৳320       │ ← Selected
│ 🛺 CNG       ৳425        │
│ 🚗 Car       ৳540        │
├──────────────────────────┤
│ Distance: 8.3 km         │
│ Time: ~25 minutes        │
│ ⚠️ Peak hour (1.5x)      │
│                          │
│ [Confirm Booking]        │
└──────────────────────────┘


Technology:
                                                * API: Google Directions API (distance/time)
                                                * Database: PostgreSQL (fare_rules table)
                                                * Logic: Node.js backend (calculation)
                                                * Caching: Redis (surge multiplier - 60s cache)
Formula:
Base_Fare = Base + (Distance × Distance_Rate) + (Time × Time_Rate)
Final_Fare = Base_Fare × Surge_Multiplier
Final_Fare = Round to nearest ৳5
If Final_Fare < Minimum_Fare → Use Minimum_Fare


Why this method:
                                                * Industry standard (Uber/Pathao)
                                                * Fair for driver (time compensated)
                                                * Transparent for rider
                                                * Flexible pricing
                                                * Easy to update rates

How it works:
Backend calculates every 2 minutes:
1. Count active ride requests per zone
2. Count available drivers per zone
3. Calculate demand/supply ratio
4. Apply color coding
5. Push to all drivers via WebSocket


Algorithm:


zones = ['Gulshan', 'Banani', 'Dhanmondi', ...]
for zone in zones: active_requests = count_rides(zone, status='searching') available_drivers = count_drivers(zone, status='online')
if available_drivers == 0: color = 'red' surge = 2.0 else: ratio = active_requests / available_drivers
if ratio > 2.0:
  color = 'red', surge = 2.0
elif ratio > 1.0:
  color = 'orange', surge = 1.5
elif ratio > 0.5:
  color = 'yellow', surge = 1.2
else:
  color = 'green', surge = 1.0


broadcast_to_drivers(zone, color, surge, requests)

🚀 RideShare AI Pro - Master Feature List
📱 Category 1: Customer/Rider Features (কাস্টমার/রাইডার)
Phase 1: Onboarding & Profile
                                                1. Phone-Based Registration: পাসওয়ার্ড ছাড়াই ফোন নম্বর এবং 6-digit SMS OTP (Twilio/Supabase) দিয়ে দ্রুত অ্যাকাউন্ট তৈরি ও অটোমেটিক লগইন (JWT token)।
                                                2. Profile Management: নাম, ছবি, জন্মতারিখ (১৮+ ভেরিফিকেশন) এবং ইমার্জেন্সি কন্টাক্ট যুক্ত করার সুবিধা। ছবি ক্লায়েন্ট-সাইডে কম্প্রেস হয়ে ক্লাউডে (Supabase Storage) সেভ হবে।
Phase 2: Ride Booking & Matching
3. Google Maps & Location Services: জিপিএস দিয়ে ইউজারের কারেন্ট লোকেশন ডিটেক্ট করা, ম্যাপ ড্র্যাগ করা এবং Google Places API দিয়ে পিকআপ/ড্রপ লোকেশন সার্চ করা।
4. Smart Fare Calculation: Base fare + Distance + Time (যদি ট্রাফিক থাকে) এর ওপর ভিত্তি করে ভাড়া হিসাব করা। রিয়েল-টাইম ডিমান্ড ও সাপ্লাইয়ের ওপর ভিত্তি করে ডাইনামিক Surge Pricing অ্যাপ্লাই করা।
5. Ride Booking & Finding Drivers: ভাড়া দেখে "Confirm Booking" করলে ডাটাবেসে রাইড ক্রিয়েট হওয়া এবং ব্যাকএন্ডে (PostGIS/Redis) ৫ কিলোমিটারের মধ্যে থাকা অ্যাভেইলেবল ড্রাইভার খোঁজা শুরু করা।
6. Driver Search Status: ড্রাইভার খোঁজার সময় স্ক্রিনে অ্যানিমেশনসহ "Searching for driver..." স্ট্যাটাস দেখানো।
7. Driver Found Notification: ড্রাইভার রিকোয়েস্ট অ্যাকসেপ্ট করলে তার ছবি, রেটিং, গাড়ির ডিটেইলস এবং পৌঁছানোর আনুমানিক সময়সহ রাইডারকে ইনস্ট্যান্ট পুশ নোটিফিকেশন পাঠানো।
Phase 3: Live Tracking & Execution
8. Real-Time Driver Tracking: Firebase/Socket.io ব্যবহার করে প্রতি ৫ সেকেন্ড পরপর ম্যাপে ড্রাইভারের লাইভ লোকেশন আপডেট করা।
9. ETA Updates: ট্রাফিকের ওপর ভিত্তি করে ড্রাইভার পৌঁছাতে কতক্ষণ লাগবে তা রিয়েল-টাইমে হিসাব করে দেখানো।
10. Pickup OTP Verification: রাইডারের অ্যাপে একটি ৪-ডিজিটের সিকিউরিটি কোড জেনারেট হওয়া, যা পিকআপের সময় ড্রাইভারকে দিয়ে ভেরিফাই করাতে হবে।
11. Ride Progress Tracking: রাইড চলাকালীন ম্যাপে রুট, বাকি থাকা দূরত্ব এবং ড্রপ লোকেশনে পৌঁছানোর সময় লাইভ দেখা।
Phase 4: Communication & Add-ons
12. In-App Chat: রাইড চলাকালীন Socket.io দিয়ে রিয়েল-টাইম টেক্সট মেসেজ আদান-প্রদান করা।
13. In-App Voice Call: WebRTC ব্যবহার করে ফোন নম্বর গোপন রেখে ইন্টারনেট দিয়ে সরাসরি কল করা।
14. Schedule-a-Ride: ১ ঘণ্টা থেকে ৭ দিন আগে advance বুকিং করে রাখা।

🚖 Category 2: Driver Features (ড্রাইভার)
Phase 1: Driver Onboarding
15. Driver Registration: 'Driver' রোল সিলেক্ট করে অ্যাকাউন্ট খোলা।
16. Document Upload: NID, ড্রাইভিং লাইসেন্স, গাড়ির ছবি ও ব্যাংক ডিটেইলস আপলোড করা।
17. Pending Verification: অ্যাডমিন প্যানেল থেকে ভেরিফাই না হওয়া পর্যন্ত প্রোফাইলের স্ট্যাটাস 'Pending' থাকা।
Phase 2: Driver Operations & Matching
18. Go Online/Offline Toggle: রাইড রিকোয়েস্ট রিসিভ করার জন্য অনলাইনে আসা বা অফলাইনে যাওয়া।
19. Ride Request Notification (with Auto-decline): কাছাকাছি বুকিং হলে ৩০ সেকেন্ডের টাইমারসহ পুশ নোটিফিকেশন পাওয়া।
20. Accept/Decline Ride: ফার্স্ট-কাম-ফার্স্ট-সার্ভ ভিত্তিতে রাইড অ্যাকসেপ্ট বা ডিক্লাইন করা। কেউ ডিক্লাইন করলে বা ৩০ সেকেন্ড পার হলে স্বয়ংক্রিয়ভাবে পরবর্তী ড্রাইভারের কাছে রিকোয়েস্ট যাওয়া।
Phase 3: Ride Execution
21. Navigate to Pickup: রিকোয়েস্ট অ্যাকসেপ্ট করার পর ম্যাপের নেভিগেশন ফলো করে ইউজারের কাছে পৌঁছানো।
22. Pickup OTP Verification: রাইডারের কাছ থেকে ৪-ডিজিটের পিন কোড শুনে অ্যাপে মিলিয়ে ভেরিফাই করা।
23. Start Ride: ওটিপি ভেরিফিকেশন সফল হলে "Start Ride" ট্যাপ করে জিপিএস ট্র্যাকিং শুরু করা।
24. Navigation During Ride: গুগল ম্যাপস ফলো করে গন্তব্যের দিকে যাওয়া এবং রুটের জিপিএস পয়েন্টগুলো সেভ করা।

Feature 4: Fare Calculation
কী হবে: Pickup ও Drop select করার পরে automatic fare calculate হবে
Calculation Formula:
Total Fare = Base Fare + (Distance × Distance Rate) + (Time × Time Rate) × Surge Multiplier


Example:
Bike ride: Gulshan 2 → Dhanmondi
- Base fare: ৳40
- Distance: 8.5 km × ৳15/km = ৳127.50
- Time: 25 min × ৳2/min = ৳50
- Subtotal: ৳40 + ৳127.50 + ৳50 = ৳217.50
- Surge (1.2x): ৳217.50 × 1.2 = ৳261
- Rounded: ৳260


Step-by-step Flow:
1. After Route Selection:
   - User pickup ও drop confirm করেছে
   - System automatically calculate করবে


2. Backend Calculation:
   - Google Directions API call করবে:
     * Origin: Pickup coordinates
     * Destination: Drop coordinates
     * Mode: Driving
     * Traffic: Yes (duration_in_traffic)
   
   - Response পাবে:
     * Distance: 8.5 km
     * Duration: 25 minutes (without traffic)
     * Duration in traffic: 32 minutes (current)


   - Database থেকে fetch করবে:
     * Vehicle type: Bike/CNG/Car
     * Base fare: ৳40 (Bike)
     * Distance rate: ৳15/km
     * Time rate: ৳2/min
   
   - Redis cache check করবে surge:
     * Current time: 6:30 PM (peak hour)
     * Demand/Supply ratio
     * Surge multiplier: 1.2x


   - Calculate করবে final fare


3. Display to User:
   - Screen এ card আসবে:
   
   "Estimated Fare: ৳260"
   
   - Breakdown button থাকবে (optional)
   - Click করলে details:
     * Base: ৳40
     * Distance (8.5 km): ৳127.50
     * Time (25 min): ৳50
     * Surge (1.2x): +৳52.50
     * Total: ৳260
   
   - Vehicle options থাকবে:
     * Bike: ৳260 (selected)
     * CNG: ৳380
     * Car: ৳520
   
   - Switch করলে re-calculate


4. Price Validity:
   - Fare 5 minutes valid
   - Timer show করবে: "Price valid for 4:32"
   - Expire হলে re-calculate button


User Experience:
                                                * Instant calculation (< 2 seconds)
                                                * Transparent breakdown
                                                * Multiple vehicle options
                                                * Current traffic consideration
                                                * Surge alert যদি থাকে
Technology:
                                                * Google Directions API (distance + time)
                                                * PostgreSQL (fare rules table)
                                                * Redis (surge cache, 60s TTL)
                                                * Backend calculation logic (Node.js)

Feature 9: Pickup OTP Verification
কী হবে: Driver pickup location এ পৌঁছানোর পর rider একটা 4-digit code দেখাবে। Driver সেটা verify করবে তারপর ride শুরু হবে।
কেন দরকার?
                                                * Wrong passenger উঠে গেলে problem
                                                * Fraud prevention
                                                * Accountability (কে কার সাথে ride করছে)
Real-Life Scenario:
Scene: Gulshan 2, Road 12
Time: 6:45 PM, rush hour
Situation: 3 জন মানুষ দাঁড়িয়ে আছে bike এর জন্য


Person A: Ahmed (আমাদের rider)
Person B: Random person ও bike খুঁজছে
Person C: আরেকজন rider, different booking


Driver Rahim আসলো। তিনজনের কাছেই যেতে পারতো!


Without OTP:
❌ Driver: "Ahmed?"
❌ Person B (scammer): "Yes, that's me!" (ফ্রি ride নিতে চায়)
❌ Wrong person উঠে গেলো
❌ Real Ahmed রয়ে গেলো
❌ Chaos!


With OTP:
✅ Driver: "Your pickup code?"
✅ Person B: "Uh... what code?" (caught!)
✅ Ahmed: "5829"
✅ Driver phone এ verify করলো
✅ ✓ Matched!
✅ Right person confirmed
✅ Ride starts safely


Step-by-step Flow:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PART 3: CODE VERIFICATION (Critical!)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


6. Rider Meets Driver:
   - Physical meeting হলো
   - Driver asks: "আপনার code?"
   - Rider shows phone অথবা বলে: "5829"


7. Driver Enters Code:
   - 4 boxes তে type করবে: 5-8-2-9
   - Auto-submit যখন 4 digits complete


8. Backend Verification Process:
   
   Step A: Receive request
   - Driver submitted: "5829"
   - Ride ID: rid-123
   
   Step B: Security checks
   - Check attempts count:
     * Current: 0
     * Maximum allowed: 3
     * If >= 3: "Too many attempts. Contact support."
   
   Step C: Verify code
   - Fetch stored hash from database
   - Use bcrypt.compare():
     bcrypt.compare("5829", stored_hash)
     → Returns: true/false
   
   Step D: Result handling
   
   If CORRECT (true):
   ✅ Update database:
      - otp_verified = true
      - status = 'started'
      - started_at = NOW()
      - driver_arrived_at = (stored earlier)
   
   ✅ Socket.io emit করবে both apps:
      - Rider: "Ride started! 🚗"
      - Driver: "Verification successful!"
   
   ✅ GPS tracking activate করবে
   
   ✅ Navigation start হবে drop location এর দিকে
   
   If WRONG (false):
   ❌ Increment attempts: 0 → 1
   
   ❌ Show error:
      "Incorrect code! 2 attempts remaining."
   
   ❌ If 3rd wrong attempt:
      "Too many failed attempts!"
      "Ride cancelled for security."
      "Support will contact you."
      
      → Automatic actions:
      - Ride cancelled
      - Both parties notified
      - Admin alert triggered
      - Investigation flag
      - Possible fraud attempt logged

Security Features:
1. Hashing (bcrypt):
   - Plain code কখনো database এ নেই
   - Even database hack হলেও useless
   - bcrypt slow by design (brute-force prevention)


2. Attempt Limiting:
   - Max 3 tries
   - Prevents guessing attack
   - Auto-investigation trigger


3. Time Validity:
   - Code generated থেকে 1 hour valid
   - Expired হলে new ride book করতে হবে
   - Prevents code reuse


4. Uniqueness:
   - Same code একই দিনে 2 বার use হবে না
   - 10,000 possible combinations (0000-9999)
   - Daily pool থেকে select


5. Audit Trail:
   - Every attempt logged:
     * When entered
     * By which driver
     * Success/failure
     * IP address
   - Investigation করা যায়

**Database Schema (Payment-related):**

```sql
-- Payments table
CREATE TABLE payments (
  id UUID PRIMARY KEY,
  ride_id UUID REFERENCES rides(id),
  amount DECIMAL(10,2) NOT NULL,
  payment_method VARCHAR(20), -- 'cash', 'card', 'wallet'
  status VARCHAR(20), -- 'pending', 'completed', 'failed', 'disputed'
  
  -- Commission split
  platform_commission DECIMAL(10,2),
  driver_earning DECIMAL(10,2),
  
  -- Timestamps
  paid_at TIMESTAMP,
  created_at TIMESTAMP DEFAULT NOW(),
  
  -- Metadata
  currency VARCHAR(3) DEFAULT 'BDT',
  receipt_url TEXT,
  
  -- Dispute handling
  dispute_status VARCHAR(20), -- null, 'reported', 'resolved'
  dispute_reason TEXT,
  
  -- Verification
  verified_by VARCHAR(20), -- 'driver', 'rider', 'system', 'admin'
  
  INDEX idx_ride_id (ride_id),
  INDEX idx_status (status),
  INDEX idx_paid_at (paid_at)
);

-- Driver settlements (weekly/monthly)
CREATE TABLE driver_settlements (
  id UUID PRIMARY KEY,
  driver_id UUID REFERENCES users(id),
  
  -- Period
  settlement_date DATE NOT NULL,
  period_start DATE,
  period_end DATE,
  
  -- Amounts
  total_collected DECIMAL(10,2),
  platform_commission DECIMAL(10,2),
  driver_earning DECIMAL(10,2),
  
  -- Settlement
  settlement_status VARCHAR(20), -- 'pending', 'paid', 'overdue'
  payment_method VARCHAR(20),
  transaction_reference VARCHAR(100),
  settled_at TIMESTAMP,
  
  -- Rides count
  total_rides INTEGER,
  
  INDEX idx_driver_date (driver_id, settlement_date),
  INDEX idx_status (settlement_status)
);

-- Payment disputes
CREATE TABLE payment_disputes (
  id UUID PRIMARY KEY,
  payment_id UUID REFERENCES payments(id),
  ride_id UUID REFERENCES rides(id),
  
  -- Parties
  reported_by UUID, -- user_id
  reported_against UUID, -- user_id
  
  -- Dispute details
  reason TEXT NOT NULL,
  evidence_urls TEXT[], -- Photos, screenshots
  
  -- Status
  status VARCHAR(20), -- 'open', 'investigating', 'resolved', 'closed'
  resolution TEXT,
  resolved_by UUID, -- admin_id
  resolved_at TIMESTAMP,
  
  -- Financial impact
  refund_amount DECIMAL(10,2),
  refund_issued BOOLEAN DEFAULT FALSE,
  
  created_at TIMESTAMP DEFAULT NOW(),
  
  INDEX idx_status (status),
  INDEX idx_ride (ride_id)
);
```

**Security Measures:**

```
1. Double-Entry Bookkeeping:
   - Every payment recorded twice:
     * Debit: Rider account
     * Credit: Driver account
   - Platform commission tracked separately
   - Sum always zero (balanced)
   - Prevents accounting errors

2. Idempotency:
   - Payment confirmation can't be done twice
   - Database constraint: UNIQUE(ride_id)
   - If driver clicks "Confirm" twice:
     * First click: Success
     * Second click: "Already confirmed"
   - Prevents duplicate earnings

3. Audit Trail:
   - Every payment action logged:
     * Who initiated
     * When
     * What changed
     * Why (reason)
   - Immutable log (append-only)
   - Compliance requirement
   - Investigation tool

4. Fraud Detection:
   - Pattern monitoring:
     * Driver confirms but rider disputes (repeatedly)
     * Unusually high fares
     * Frequent disputes
     * GPS anomalies (route manipulation)
   
   - Auto-flags:
     * 3+ disputes in 1 week → Review driver
     * Fare > 200% of estimate → Investigate
     * Same rider-driver disputes → Ban both
   
   - ML-based (future):
     * Predict fraudulent patterns
     * Anomaly detection
     * Risk scoring

5. Encryption:
   - Payment data encrypted at rest
   - TLS for data in transit
   - PCI DSS compliance (when adding cards)
   - No plain-text sensitive data
```
